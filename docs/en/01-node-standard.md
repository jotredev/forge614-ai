# 01 — Node standard

> Like a city's building code: it does not say which house to build, but every new house must comply with it and an inspector checks it.

## How to read `standard/STANDARD.md`

The **Node Standard** is the binding norm for every repository in the ecosystem. It lives in `standard/STANDARD.md` with its twin `standard/STANDARD.en.md`; in its text, "must" means that the verifier checks it or that human review demands it before merging. It has thirteen numbered sections and one appendix:

| Section | Topic |
| --- | --- |
| 1 | Node identity and contract (`forge614.node.json`, `CONTRACT.md`) |
| 2 | Repository structure and layers (`modules`, `app`, `infrastructure`, `interfaces`) |
| 3 | Stack (strict TypeScript, Bun, Zod at every boundary) |
| 4 | Machine contracts (JSON on stdout, errors on stderr, exit codes) |
| 5 | Mandatory patterns, named by problem |
| 6 | Installation (three operating systems, installers from template) |
| 7 | Release, versioning and workflows |
| 8 | Documentation |
| 9 | Work process and decision records |
| 10 | AI agent behavior rules |
| 11 | Cross-cutting security |
| 12 | New AI agents |
| 13 | Minimal footprint and replaceable pieces |
| Appendix A | Canonical pattern of every element in the ecosystem |

Where a decision originated a point, the norm cites the corresponding record (sections 4, 6, 7, 8, 12 and 13); the records are in `docs/decisions/` (document 02 explains how they are born). This repository is the first to comply with the norm; the other nodes adopt it during their alignment. The data schemas the norm names (pointer, rule manifest, pack, support matrix, error envelope, NDJSON event, decisions index, forbidden mentions) exist twice: as a Zod schema in `src/modules/standard/schemas/` and as a JSON Schema copy in `standard/schemas/`, generated by `bun run schemas:generate`; `bun run schemas:generate --check` fails with `SCHEMAS_DRIFT` if the copies do not match.

## Standard versioning

Two files pin the version:

- `standard/VERSION` holds the standard's version (today `1.1.1`) in SemVer format (`MAJOR.MINOR.PATCH`). It appears in the title of `STANDARD.md`, in the archive name (`standard-1.1.1.tar.gz`) and in the files rendered from templates (variable `STANDARD_VERSION`, document 03).
- `forge614.node.json` is the **node pointer**: `{ schemaVersion: 1, node, kind, standard: { version, sha256 }, ecosystem? }`. `standard.version` is the standard version the node declares to comply with and `standard.sha256` the fingerprint of the standard archive for that version; `kind` tells `product` (installable) from `internal` (nobody installs it by hand); `ecosystem`, optional in the schema (record 0022), names the group the node belongs to. The `NodePointerSchema` schema (`src/modules/standard/schemas/node-pointer.ts`) validates it and rejects unknown fields.

In this repository the pointer carries the fingerprint of the archive that `bun run standard:pack` produces from `standard/` itself; `bun run standard:pack --check` checks that they still match (document 04).

## How a node pins and bumps the version

A node **pins** the version by writing `standard.version` and `standard.sha256` in its `forge614.node.json`; the fingerprint is that of the archive published for that version, which matches the one in the `forge614-ai` pointer. No node copies `standard/` into its tree: it carries only the pointer (record 0009).

To **bump** the version, the node changes both fields to the new version, renders the templates again (document 03), reviews the diff and runs its verification. The intended practice is that bumping the version adds checks without renaming or removing existing ones. Today, editing another node's pointer is manual; `bun run standard:pack --update-pointer` only rewrites the fingerprint in this repository's pointer.

## Planned local cache

Today the verifier runs only on this repository and reads `standard/` straight from the tree. Record 0009 foresees that each node's verifier fetches the published version of the standard, caches it under `~/.forge614/` and checks the fingerprint against the pointer before using it; per section 6 of the norm, `FORGE614_HOME` replaces `~/.forge614` in every node. That cache, and the verifier that runs on other repositories, arrive with phase 0.2; they do not exist in this tree.
