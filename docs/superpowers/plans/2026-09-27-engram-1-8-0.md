# Engram 1.8.0 — la misma memoria en otra Mac (plan)

> **For agentic workers:** este plan se ejecuta con `superpowers:subagent-driven-development` (una tarea = un subagente con contexto limpio) o `superpowers:executing-plans` (ejecución en línea) según decida quien lo abra; ninguna tarea se empieza sin leer primero su sección completa (Files, Interfaces, Pruebas, Criterio de «hecho»).

**Goal:** publicar `forge614-engram` 1.8.0: la memoria del propietario (proyecto, libreta personal y tablero del ecosistema) queda en Neon (nube) y es la misma en cualquiera de sus dos Mac, sin escritura simultánea, sin que el arranque se sienta más lento, y sin perder nada sin internet. Instalar 1.8.0 y activar la nube en las dos Mac.

**Architecture:** esquema SQLite local nuevo, nivel 12 (enrollment explícito con `cloud on`, igual que el nivel 11 de memoria inteligente); una cola de pendientes (outbox) alimentada por disparadores SQL sobre cada tabla que viaja; una tarea en segundo plano dentro del servidor MCP que sube la cola y baja lo nuevo de una tabla de cambios numerada en Neon (`forge614_sync.changes`); aplicación de cambios bajados con reglas de conflicto por tabla y filtro de secretos; identidad de proyecto por remoto de Git cuando falta `.forge614/project.json`.

**Tech Stack:** Bun + `bun:sqlite` (SQLite local), `Bun.SQL` contra PostgreSQL/Neon (ya en uso, `src/infrastructure/postgres/replica.ts`), TypeScript, `bun test`.

**Spec:** `docs/superpowers/specs/2026-09-27-engram-1-8-0-otra-mac-design.md` (aprobado por el propietario el 2026-09-27), secciones 3–17, decisiones M1–M13.

**Origen:** diseño aprobado el 2026-09-27, reemplaza el esbozo `forge614-engram/.agents/plans/2026-09-23--1.7.0-ecosystem-replication.md` (acta 0024, evolución aditiva).

**Dónde se ejecuta:** en `~/Desktop/forge614-engram`, rama nueva `work/1.8.0-otra-mac` desde `main` = `origin/main` = `69d8e5c` (v1.7.2). Este plan y sus parches viven en `forge614-ai`, rama `docs/engram-1-8-0-spec`. Una tarea = una sesión nueva, etiqueta `[Engram · T<n>]`. Cada prompt se guarda antes de lanzarse en `~/.forge614/orquestador/forge614-ai/prompts/engram-1.8.0/Tn-rK.md` y su salida en `…/reportes/engram-1.8.0/`.

## Global Constraints

- Todo comando con `rtk` delante; `rtk proxy` para salida sin filtrar.
- Nivel de esquema 12 solo se activa con `cloud on` (D1); sin nube, la base y el arranque no cambian (M5).
- 1.7.2 no abre una base de nivel 12: responde `DATABASE_VERSION`. `cloud on` se corre después de instalar 1.8.0 y de cerrar **todas** las sesiones que usan la base, con el control previo de procesos (guía §4, lección Engram T10/T10b: verificar hora de inicio y programa padre; detenerse si queda alguno anterior).
- `POSTGRES_URL` en `~/.forge614/engram/.env` sigue siendo la única variable de conexión (diseño §10) y apunta a Neon; no hay dos nubes a la vez. El `.env` suma `FORGE614_ENGRAM_INSTALLATION_ID` (D9).
- La dirección de Neon nunca pasa por una sesión de IA: en el uso real, `cloud on` la pide en la terminal del propietario (entrada oculta); en el laboratorio se carga de un archivo sin imprimirla (D13).
- TLS verificado obligatorio fuera de loopback, mismo criterio de `postgresOptions` (`src/infrastructure/postgres/replica.ts:5-23`).
- Espera al arrancar con nube prendida: máximo 1000 ms (`AbortSignal.timeout(1000)` o equivalente), nunca más (M13, D8).
- Ciclo de la tarea en segundo plano: 30 s de intervalo mientras el servidor MCP vive, más un ciclo extra al guardar con retraso corto para agrupar (D7).
- Aviso de cola vieja: pendiente más viejo con más de 24 h → dato en `memory_session_start` (D11, M11).
- Sin nombres de productos externos (acta 0012): revisar `standard/forbidden-mentions.json` antes de escribir cualquier documento de `forge614-ai`.
- Commits convencionales en inglés, sin líneas de atribución ni menciones a ninguna IA.
- Suite como en CI: `FORGE614_TEST_POSTGRES_BIN=$(pg_config --bindir) bun test`; toda prueba omitida se justifica.
- Código literal fuera del plan: cada tarea trae un parche `2026-09-27-engram-1-8-0-t<n>.patch`, probado en laboratorio (copia limpia con `git archive`) antes de entregarse (D12, guía §1).
- Todo campo de texto nuevo que viaja (D5) pasa por el filtro de secretos existente (`writes.ts:231`) y trae una prueba propia por campo (guía §4).
- Antes de instalar sobre archivos reales del propietario (T9, T10): laboratorio con HOME falso (guía §4).
- Comentarios del código en español (D15): desde T3b, todo parche trae su código documentado según la norma de la sección J, y el laboratorio corre `cobertura-jsdoc.ts` (sección J) sobre los archivos que toca, con 0 faltantes.
- Idioma (D16): nombres de código, SQL, códigos de error, nombres y datos de pruebas y mensajes de commit en inglés; comentarios en español. Hasta 1.9.0 (que agrega el catálogo es/en), los textos nuevos para la persona (errores, salida de la terminal) siguen el idioma de los textos vecinos del mismo archivo, para que 1.9.0 los pase todos juntos al catálogo.

## Review Focus

Las cinco fallas más probables que ninguna prueba «feliz» cubre, con la prueba que se agrega a la tarea dueña:

1. **La guardia de aplicación no se libera si el aplicador lanza una excepción a mitad de la transacción**, dejando los disparadores apagados para siempre y la cola dejando de crecer con cambios locales reales. → T3: prueba que fuerza un error al aplicar una fila y verifica que, tras el rollback, un guardado local nuevo sí encola.
2. **Reintento infinito y silencioso de un cambio corrupto** (payload que no valida) bloquea el resto de la cola en orden estricto. → T3: prueba de un payload inválido en medio de una tanda; se salta con aviso y sigue con el resto.
3. **La espera de 1000 ms al arrancar no se cancela** si Neon responde justo después del corte, dejando una promesa huérfana que compite por el mismo `sqlite`/conexión con la tarea en segundo plano. → T4: prueba con `AbortSignal` y un mock que resuelve 50 ms después del corte; se verifica que no hay doble aplicación ni excepción no capturada.
4. **`cloud off` no vacía ni marca la cola pendiente**, y una `cloud on` posterior con otra URL de Neon sube filas viejas al proyecto equivocado. → T5: prueba `cloud off` con pendientes en la cola → `cloud status` los sigue mostrando → `cloud on` con otra base → como es otra nube (D14), vuelve a encolar toda la memoria local y baja desde 0; con la misma base, la cola y `last_applied_id` se conservan.
5. **Identidad por remoto de Git compara mal direcciones equivalentes** (con y sin `.git`, `git@`/`ssh://` vs `https://`, mayúsculas de host) y crea proyectos duplicados. → T3b: banco de pares equivalentes/no equivalentes (incluye con y sin credenciales embebidas, con y sin puerto) como prueba fija.

## Decisiones

- **D1.** Nivel de esquema 12 en la misma base SQLite, activado SOLO por `cloud on` (enrollment explícito, igual que el 11). Sin nube, la base no cambia y el arranque es el de hoy. Contiene: cola de pendientes (tabla outbox), el número del último cambio aplicado desde Neon, el origen de cada cambio y los avisos pendientes (conflicto, cola vieja). Motivo: la cola se escribe en la MISMA transacción que el guardado, así no se pierde nada si se cierra la laptop. Consecuencia: 1.7.2 no abre una base de nivel 12 (responde `DATABASE_VERSION`); por eso `cloud on` se corre después de instalar 1.8.0 y cerrar todas las sesiones que usan la base (lección de la guía §4, Engram T10/T10b). *(Decisión técnica del orquestador, confirmada por el propietario el 2026-09-27 (opción A); alternativa descartada: base aparte `sync.db` — no toca el esquema, pero el guardado y la cola no quedan en una misma transacción.)*
- **D2.** La cola se alimenta con disparadores SQL (triggers) de nivel 12 sobre cada tabla que viaja (sección 5 del diseño); al aplicar cambios bajados de Neon, los disparadores no vuelven a encolar (guardia de una fila que el aplicador prende y apaga dentro de su transacción). Cada fila de la cola lleva la imagen completa de la fila cambiada (JSON), el tipo (tabla) y la operación.
- **D3.** En Neon: `forge614_sync.changes(id bigserial primary key, change_id text not null unique, installation_id uuid not null, kind text not null, op text not null, payload jsonb not null, created_at timestamptz not null default now())`, creada si falta. `change_id` es el identificador de la fila de la cola local (`cloud_outbox.change_id`, 32 caracteres al azar): si Neon guarda un lote pero la respuesta se pierde, el siguiente ciclo lo vuelve a subir y `on conflict (change_id) do nothing` evita el duplicado (hallazgo 4113885719 de CodeRabbit, PR #18); `op` distingue alta, cambio y borrado; las tablas `revisions`/`state` de hoy no se tocan. Misma variable `POSTGRES_URL` y misma verificación de TLS fuera de loopback (`replica.ts:5-23`).
- **D4.** Conflicto de recuerdos: si llega una versión de un recuerdo que localmente ya cambió desde la base común, se guardan las dos como versiones; queda activa la de fecha más reciente; la otra queda en el historial; se registra un aviso que se muestra una vez en el siguiente `memory_session_start` (junto a `sessionNotice`, como dato). Nunca se detiene la sincronización. **Cómo se detecta (opción 1A, confirmada por el propietario el 2026-09-27):** Engram no guarda la versión de la que partió un cambio, así que no hay «base común» que comparar; el conflicto es una versión que llega con un número `(memory_id, version)` que localmente ya ocupa otro contenido. Esa versión se guarda con el siguiente número libre y una tabla local `cloud_version_map` (no viaja) anota la equivalencia, para que lo que llegue después apuntando a ella (el propio recuerdo, entradas de sesión, resúmenes, confirmaciones, borrados) se redirija. La numeración del historial puede diferir entre las dos Mac. Descartados: renumerar para que queden idénticas (mueve versiones a las que ya apuntan otras filas) y dejar la perdedora solo en el aviso. Las demás tablas: la fila más reciente gana, sin aviso (sesiones, resúmenes, grupos, pertenencias, fuentes).
- **D5.** El filtro de secretos se aplica a lo que llega de Neon antes de escribir (un cambio rechazado se salta y queda un aviso; no detiene la sincronización). Columnas de texto libre que viajan, verificadas por el laboratorio de T1 contra `schema.ts` de `69d8e5c` (cada una lleva prueba propia en T3): `memories.title` y `memories.content` (`schema.ts:87-88`), `memory_meta.short` (`schema.ts:227`), `projects.name` (`schema.ts:77`) y `memory_versions.snapshot` (`schema.ts:102`), que es JSON pero lleva dentro `title` y `content`: el filtro revisa esos campos anidados. No son texto libre: `sessions.kind` (CHECK `runtime`/`manual`), `ecosystem_groups.name` (slug validado por GLOB, sin columna de descripción), `memories.topic_key` (clave), `memory_meta.affects` y `confirmation_requests.response` (JSON estructurado), `confirmation_requests.requestKey` (clave); `confirmations`, `session_entries`, `session_summaries`, `ecosystem_memberships` y `ecosystem_sources` no tienen columnas de texto libre.
- **D6.** Identidad por remoto de Git (tarea T3b, opción 2A confirmada por el propietario el 2026-09-27): los proyectos viajan con su `projectId`, así que aplicar un proyecto que no existe localmente solo lo inserta. El remoto hace falta al abrir en la otra Mac una carpeta **sin** `.forge614/project.json` (forge614-engram lo ignora en Git; forge614-ai, engines, shell y model-ledger lo guardan): hoy `projects` no guarda el remoto y ningún código lee `git remote`. T3b agrega una tabla que viaja con el remoto normalizado de cada proyecto (sin credenciales, sin `.git` final, https y ssh equivalentes, host en minúsculas), se llena al ligar una carpeta con remoto `origin` y se consulta al resolver una carpeta sin archivo de identidad; si no hay coincidencia, se crea proyecto nuevo como hoy; nunca se adivina. Descartado: solo con el archivo de identidad (forge614-engram quedaría como proyecto nuevo en la otra Mac). **Detalle (reconocimiento del orquestador en copia de `0868f14`, aceptado por el propietario el 2026-09-27):** un remoto por proyecto (llave `projectId`; gana el más reciente); si dos proyectos tienen el mismo remoto, no se liga ninguno y se crea proyecto nuevo (nunca se adivina); el remoto se lee del archivo `config` del directorio Git común que `project-directory.ts` ya calcula (sin ejecutar `git` otra vez, así el arranque no se alarga; los worktrees comparten ese directorio); se anota cada vez que una carpeta se resuelve con escritura, solo si falta o cambió (así forge614-engram queda anotado en la Mac 1 sin volver a ligarlo); el remoto pasa por el filtro de secretos al guardarse y al llegar de la nube (`secretPatternOf` de `cloud-apply.ts` hoy no tiene rama para tablas nuevas). Descartados: varios remotos por proyecto (los 5 repositorios tienen un solo `origin`), leer con `git remote` (un proceso más por arranque) y anotar solo al ligar (los proyectos ya ligados nunca se anotarían).
- **D7.** Tarea en segundo plano dentro del servidor MCP (`server.ts`): arranca solo si hay nube configurada y el nivel es 12; ciclo: subir cola en orden, bajar lo posterior al último número, aplicar; intervalo de 30 s mientras el servidor vive y un ciclo al guardar (con retraso corto para agrupar). Errores de red: se reintenta en el siguiente ciclo, sin ruido.
- **D8.** Espera al arrancar (M13): `startup-context` y `memory_context`, con nube prendida, hacen un ciclo de bajada con tope de 1000 ms (`AbortSignal`/timeout); si no termina, siguen con lo local.
- **D9.** Id de instalación: UUID en `~/.forge614/engram/.env` como `FORGE614_ENGRAM_INSTALLATION_ID`, generado por `cloud on`. `cloud on --postgres-url <url>` prueba la conexión (`validatePostgres`) antes de escribir; `cloud off` quita `POSTGRES_URL` (conserva el id y la base de nivel 12, que sigue funcionando sin nube); `cloud status` (con `--json`): prendida/apagada, id de instalación, último cambio aplicado, pendientes en la cola, hora del pendiente más viejo.
- **D10.** `sync` = un ciclo ahora (subir+bajar) con el mecanismo nuevo; `sync-watch` = el mismo ciclo por intervalo, marcado obsoleto con sunset 2027-03-31 (aviso en stderr y en `help`); `sync --upgrade-format` y los formatos 1–3 quedan obsoletos, sin borrar código (acta 0024).
- **D11.** Aviso de cola vieja (M11): si el pendiente más viejo tiene más de 24 h, `memory_session_start` lo dice como dato.
- **D13.** `cloud on` sin argumentos pide la dirección en la terminal con entrada oculta y la prueba antes de guardarla; `--postgres-url <url>` queda para pruebas y laboratorio. En T9 y T10 el propietario corre `cloud on` en su propia terminal (fuera de toda sesión de IA), así la dirección no entra a ningún registro. *(Decisión técnica del orquestador, confirmada por el propietario el 2026-09-27 (opción A).)*
- **D14.** Primera sincronización (M4): `enableCloud` encola **toda** la memoria local que viaja, en la misma transacción y en orden de dependencias (proyectos, grupos, pertenencias, fuentes, recuerdos, versiones, datos de memoria inteligente, sesiones, entradas, resúmenes, confirmaciones). `cloud_state` guarda una huella de la base remota (servidor y nombre de base, sin usuario ni contraseña); si `cloud on` apunta a otra base, se trata como primera vez: se vuelve a encolar todo y se baja desde 0. *(Decisión técnica del orquestador, confirmada por el propietario el 2026-09-27 (opción A).)*
- **D15.** Código de Engram documentado en español (pedido del propietario el 2026-09-27, opciones A y A): cada archivo con un encabezado que dice qué hace; cada función, clase, método, interfaz, tipo y campo con JSDoc; los algoritmos y la lógica comentados paso a paso, línea por línea donde la línea no se entiende sola; constantes, importaciones y reexportaciones sin comentario; pruebas con encabezado y una línea antes de cada prueba. Los comentarios en inglés se traducen. Se hace antes de T3b, en cuatro tareas J1–J4 (sección J) que solo cambian comentarios; desde T3b cada parche ya trae su código documentado. Descartados: documentar solo el código nuevo y lo viejo al final (choca con todo lo hecho en medio) y después de publicar.
- **D16.** Idioma (decisión del propietario, 2026-09-27, orquestador t4; motivo: hoy el código mezcla idiomas y debe ser constante): en inglés el código (nombres de funciones, variables, tipos y archivos, SQL, códigos de error), los nombres y datos de las pruebas y los mensajes de commit; en español las explicaciones (encabezados, JSDoc, comentarios), el manual de Engram (`protocol.ts`, lo que se instala en `CLAUDE.md`/`AGENTS.md`) y las descripciones de las herramientas MCP; todo lo que ve la persona (salida de la terminal, `setup`, errores, también los que llegan por MCP) sale en el idioma elegido en Shell (`locale` de `~/.forge614/shell/preferences.json`; Shell siempre se instala con Engram y lo primero que pide es el idioma) con un catálogo es/en igual al de Shell (`src/i18n`: `types.ts`, `es.ts`, `en.ts`, `getCatalog`; sin librerías externas); inglés solo como respaldo si el archivo falta o está dañado. `docs/`: cada documento completo en su idioma; los archivos internos de `docs/handoffs` y `docs/superpowers` pasan a `.agents/` (T7). Cuándo (opción 2A): el catálogo, el manual y las descripciones en español van en su propia versión 1.9.0, justo después de 1.8.0, con pruebas de conducta de los asistentes y la versión de Engines que instale el manual nuevo. Medido en `5b6ab48`: ~437 textos del código en español (errores, `setup`, terminal) en 77 archivos; manual y descripciones en inglés; nombres de pruebas casi todos en inglés. Descartados: todo en inglés fijo, todo en español fijo, hacer idiomas dentro de 1.8.0 (retrasa la nube y mezcla riesgos) y traducir los archivos internos.
- **D12.** Forma del plan: el plan fija por tarea archivos y líneas reales, interfaces exactas (nombres y tipos), SQL de las tablas nuevas, y la lista de pruebas con lo que cada una afirma. El código literal NO va en el plan: sale de un laboratorio del orquestador por tarea (parche probado en copia limpia) y se agrega al plan como `2026-09-27-engram-1-8-0-t<n>.patch` antes de entregar la tarea, igual que en 1.7.2. Cada tarea trae «**Parche:** se agrega tras el laboratorio.» y «**Cierre de T<n>:**» vacío.

**Norma de comentarios (D15):**
1. Encabezado de cada archivo: un bloque `/** … */` al inicio que dice qué hace el archivo, para qué existe, quién lo usa y sus piezas principales. En pruebas, 1–3 líneas: qué comprueba el archivo.
2. Cada función, clase, método, interfaz, tipo y campo de interfaz (exportado o interno): JSDoc que dice qué hace y por qué; `@param` por parámetro (qué es y qué valores acepta), `@returns` y `@throws` con el código de `MemoryError` cuando lanza.
3. Algoritmos y lógica (ramas, ciclos, transacciones, consultas SQL, expresiones regulares, cálculos, reintentos): comentario `//` en cada paso, línea por línea donde la línea no se entiende sola; explica el porqué, no repite el código. Las funciones internas dentro de otra función se explican con `//`.
4. Constantes, importaciones y reexportaciones: sin comentario.
5. Pruebas: el encabezado y una línea `//` antes de cada `test`, `it` o `describe` que dice qué comprueba y por qué importa; sin línea por línea.
6. Los comentarios en inglés se traducen al español con el mismo sentido; si uno no cuadra con el código, se corrige según el código.
7. Español llano: cada término técnico se explica la primera vez que aparece en el archivo, entre paréntesis (p. ej. «transacción (grupo de cambios que se guarda completo o no se guarda)»).
8. No se cambia ni un carácter de código: ni formato, ni orden, ni espacios dentro de líneas de código, ni textos literales (un comentario dentro de un texto entre comillas o acentos graves cambia su valor); sin archivos nuevos. Si un comentario no cabe sin tocar el código, se pone en la línea de arriba.
9. Sin nombres de productos externos (`standard/forbidden-mentions.json` de `forge614-ai`) y sin sentencias `import` escritas dentro de comentarios (las reglas de arquitectura leen el texto de los archivos).
10. La sesión trabaja sola: sin subagentes, agentes en paralelo ni otras sesiones (regla firme del propietario para todo prompt, guía §2; J1-r1 lanzó 18 subagentes que se pisaron entre sí y costó $26 en vez de $2–4).
11. Cada comentario dice algo propio de lo que explica: nada de frases genéricas que sirvan para cualquier función o prueba («Describe `X`…», «Resultado que produce la operación», «Comprueba el caso indicado…»); un comentario viejo con información real se traduce, nunca se reemplaza por una frase genérica. `cobertura-jsdoc.ts` marca como relleno la misma línea repetida 8 o más veces (agregado tras J2-r2).
12. Cada frase que dice quién usa un archivo, quién llama a una función o de dónde viene un dato se comprueba en el código antes de escribirla (búsqueda de sus importaciones y llamadas con `grep`); si nadie lo usa fuera de su prueba, se dice así. Script `solo-comentarios.ts`:

```ts
// Comprueba que entre un commit base y la carpeta de trabajo solo cambiaron comentarios y espacios.
// Uso, dentro del repositorio: bun <ruta>/solo-comentarios.ts <commit base>
// Sale con 0 si cada archivo .ts cambiado da el mismo código al quitarle los comentarios; si no, 1.
// Dos comparaciones: el código impreso sin comentarios (atrapa cambios de código, tipos y textos) y las líneas
// de código tal como están escritas (atrapa líneas partidas, unidas o movidas; ignora líneas en blanco y espacios).
const ts = (await import(`${process.cwd()}/node_modules/typescript/lib/typescript.js`)).default;
const base = Bun.argv[2];
if (!base) { console.error("falta el commit base"); process.exit(2); }
const git = (...args: string[]) => {
  const r = Bun.spawnSync(["git", ...args], { stdout: "pipe", stderr: "pipe" });
  if (r.exitCode !== 0) { console.error(r.stderr.toString()); process.exit(2); }
  return r.stdout.toString();
};
const printer = ts.createPrinter({ removeComments: true });
const code = (path: string, text: string) =>
  printer.printFile(ts.createSourceFile(path, text, ts.ScriptTarget.Latest, false, ts.ScriptKind.TS));
const layout = (path: string, text: string) => {
  const sf = ts.createSourceFile(path, text, ts.ScriptTarget.Latest, true, ts.ScriptKind.TS);
  const ranges = new Map<number, number>();
  const collect = (n: import("typescript").Node) => {
    for (const r of [...(ts.getLeadingCommentRanges(text, n.pos) ?? []), ...(ts.getTrailingCommentRanges(text, n.end) ?? [])]) ranges.set(r.pos, r.end);
    n.getChildren(sf).forEach(collect);
  };
  collect(sf);
  let out = "", at = 0;
  for (const [pos, end] of [...ranges].sort((a, b) => a[0] - b[0])) { if (pos < at) continue; out += text.slice(at, pos); at = end; }
  out += text.slice(at);
  return out.split("\n").map((l) => l.replace(/\s+/g, " ").trim()).filter(Boolean).join("\n");
};
const problems: string[] = [];
const untracked = git("ls-files", "--others", "--exclude-standard").split("\n").filter(Boolean);
for (const path of untracked) problems.push(`archivo nuevo no permitido: ${path}`);
const changed = git("diff", "--name-status", base).split("\n").filter(Boolean);
let checked = 0;
for (const line of changed) {
  const [status, path] = line.split("\t");
  if (status !== "M") { problems.push(`${status} no permitido: ${path}`); continue; }
  if (!path.endsWith(".ts")) { problems.push(`solo se permiten archivos .ts: ${path}`); continue; }
  const before = code(path, git("show", `${base}:${path}`));
  const after = code(path, await Bun.file(path).text());
  checked++;
  if (before !== after) problems.push(`cambió el código, no solo comentarios: ${path}`);
  else if (layout(path, git("show", `${base}:${path}`)) !== layout(path, await Bun.file(path).text())) problems.push(`cambió la forma de las líneas de código (partidas, unidas o movidas): ${path}`);
}
console.log(`archivos .ts revisados: ${checked}`);
for (const p of problems) console.log(p);
process.exit(problems.length ? 1 : 0);
```

Script `cobertura-jsdoc.ts`:

```ts
// Lista lo que falta documentar en los archivos .ts de las carpetas o archivos dados.
// Uso, dentro del repositorio: bun <ruta>/cobertura-jsdoc.ts <carpeta o archivo>...
// Código: encabezado /** */ al inicio y JSDoc en cada función, clase, método, interfaz, tipo y campo.
// Pruebas (*.test.ts y __test-support__/, __tests__/, tests/): encabezado y un comentario antes de cada test/it/describe.
// Todos: ningún comentario que parezca escrito en inglés (más palabras comunes del inglés que del español)
// y ninguna línea de comentario de relleno (la misma frase 8 o más veces).
// Sale con 0 si no falta nada; si falta algo, lo lista con archivo:línea y sale con 1.
const ts = (await import(`${process.cwd()}/node_modules/typescript/lib/typescript.js`)).default;
import { readdirSync, statSync } from "node:fs";
import { join } from "node:path";
const roots = Bun.argv.slice(2);
if (!roots.length) { console.error("falta la carpeta o archivo"); process.exit(2); }
const files: string[] = [];
const walk = (p: string) => {
  if (statSync(p).isDirectory()) { for (const n of readdirSync(p)) if (n !== "node_modules") walk(join(p, n)); }
  else if (p.endsWith(".ts") && !p.endsWith(".d.ts")) files.push(p);
};
roots.forEach(walk);
const isTest = (p: string) => /\.test\.ts$/.test(p) || /(^|\/)(__test-support__|__tests__|tests)\//.test(p);
const missing: string[] = [];
for (const path of files.sort()) {
  const text = await Bun.file(path).text();
  const sf = ts.createSourceFile(path, text, ts.ScriptTarget.Latest, true, ts.ScriptKind.TS);
  const at = (n: import("typescript").Node) => `${path}:${sf.getLineAndCharacterOfPosition(n.getStart(sf)).line + 1}`;
  const hasJsDoc = (n: import("typescript").Node) =>
    (ts.getLeadingCommentRanges(text, n.getFullStart()) ?? []).some((r) => text.startsWith("/**", r.pos));
  const hasComment = (n: import("typescript").Node) => (ts.getLeadingCommentRanges(text, n.getFullStart()) ?? []).length > 0;
  if (!/^(#![^\n]*\n)?\s*\/\*\*/.test(text)) missing.push(`${path}:1 encabezado del archivo`);
  const seen = new Set<number>();
  const english = /\b(the|is|are|and|of|to|when|this|that|with|from|for|it|only|must|be|an|or|which|by)\b/gi;
  const spanish = /\b(el|la|los|las|de|del|que|y|en|un|una|se|por|con|para|es|lo|al|cuando|solo|como|o)\b/gi;
  const scan = (n: import("typescript").Node) => {
    for (const r of ts.getLeadingCommentRanges(text, n.getFullStart()) ?? []) {
      if (seen.has(r.pos)) continue;
      seen.add(r.pos);
      const body = text.slice(r.pos, r.end).replace(/`[^`]*`/g, " ");
      const en = body.match(english)?.length ?? 0, es = body.match(spanish)?.length ?? 0;
      if (en >= 3 && en > es) missing.push(`${path}:${sf.getLineAndCharacterOfPosition(r.pos).line + 1} comentario en inglés`);
    }
    n.getChildren(sf).forEach(scan);
  };
  scan(sf);
  if (isTest(path)) {
    const visit = (n: import("typescript").Node) => {
      if (ts.isExpressionStatement(n) && ts.isCallExpression(n.expression)) {
        const callee = n.expression.expression.getText(sf);
        if (/^(test|it|describe)(\.(skip|only|if\(.*\)|each\(.*\)|todo))*$/.test(callee.replace(/\s+/g, "")) && !hasComment(n))
          missing.push(`${at(n)} comentario antes de ${callee}(…)`);
      }
      ts.forEachChild(n, visit);
    };
    visit(sf);
    continue;
  }
  const visit = (n: import("typescript").Node, depth: number) => {
    const named = (n as { name?: import("typescript").Node }).name?.getText(sf) ?? "(sin nombre)";
    if (ts.isFunctionDeclaration(n) || ts.isClassDeclaration(n) || ts.isInterfaceDeclaration(n) || ts.isTypeAliasDeclaration(n) || ts.isEnumDeclaration(n)) {
      if (depth === 0 && !hasJsDoc(n)) missing.push(`${at(n)} JSDoc de ${named}`);
    } else if ((ts.isMethodDeclaration(n) || ts.isConstructorDeclaration(n) || ts.isGetAccessor(n) || ts.isSetAccessor(n)) && ts.isClassLike(n.parent)) {
      if (!hasJsDoc(n)) missing.push(`${at(n)} JSDoc del método ${named}`);
    } else if ((ts.isPropertySignature(n) || ts.isMethodSignature(n)) && ts.isInterfaceDeclaration(n.parent)) {
      // Un campo que comparte su línea con la interfaz o con otro campo no se parte (norma, punto 8):
      // lo explica el JSDoc de la interfaz, así que solo se exige JSDoc propio al campo que ocupa su línea.
      const line = (x: import("typescript").Node) => sf.getLineAndCharacterOfPosition(x.getStart(sf)).line;
      const alone = line(n) !== line(n.parent) && n.parent.members.filter((m) => line(m) === line(n)).length === 1;
      if (alone && !hasJsDoc(n)) missing.push(`${at(n)} JSDoc del campo ${named}`);
    } else if (ts.isVariableStatement(n) && depth === 0) {
      const fn = n.declarationList.declarations.some((d) => d.initializer && (ts.isArrowFunction(d.initializer) || ts.isFunctionExpression(d.initializer)));
      if (fn && !hasJsDoc(n)) missing.push(`${at(n)} JSDoc de ${n.declarationList.declarations[0].name.getText(sf)}`);
    }
    const inner = ts.isFunctionLike(n) || ts.isClassLike(n) ? depth + 1 : depth;
    ts.forEachChild(n, (c) => visit(c, ts.isClassLike(n) ? depth : inner));
  };
  sf.statements.forEach((s) => visit(s, 0));
}
// Relleno: la misma línea de comentario (sin contar lo que va entre acentos graves) repetida 8 o más veces en los
// archivos revisados es una frase genérica, no una explicación; @param y @throws se repiten con razón.
const repeated = new Map<string, string[]>();
for (const path of files) {
  (await Bun.file(path).text()).split("\n").forEach((l, i) => {
    const t = (l.match(/^\s*(?:\/\/+|\/\*\*|\*)\s*(.*?)\s*(?:\*\/)?\s*$/)?.[1] ?? "").replace(/`[^`]*`/g, "`X`").trim();
    if (t.length < 12 || /^@(param|throws)\b/.test(t)) return;
    repeated.set(t, [...(repeated.get(t) ?? []), `${path}:${i + 1}`]);
  });
}
for (const [t, at] of repeated) if (at.length >= 8) missing.push(`${at[0]} comentario de relleno repetido ${at.length} veces: «${t.slice(0, 80)}»`);
console.log(`archivos revisados: ${files.length}; faltan: ${missing.length}`);
for (const m of missing) console.log(m);
process.exit(missing.length ? 1 : 0);
```

## Medición del arranque

Mediana de 10 corridas en tiempo de `forge614-engram startup-context --directory <ruta-absoluta> --json --format 2` (los argumentos que usa el gancho de Engines 1.13.0, `forge614-engines/src/infrastructure/engram/startup-context-client.ts:216-217`; el gancho no pone tope de tiempo) y de `memory_context` por MCP. Criterios: sin nube igual que 1.7.2 ±2 ms (misma máquina, misma base copiada); con nube ≤ 1 s más en el peor caso, anotando despierta y dormida (Neon suspendida). En tokens: presupuesto de acta 0027 §8 (≤3000 caracteres de bloque + manual).

Script del orquestador (`medir-arranque.ts` en su scratchpad; no entra al repositorio de Engram). Antes de usarlo en L1 se prueba contra 1.7.2 y una base copiada: si el saludo MCP o los argumentos no cuadran, se corrige aquí.

```typescript
#!/usr/bin/env bun
// medir-arranque.ts — mediana de N corridas de startup-context y memory_context
import { spawnSync } from "bun";

function median(values: number[]): number {
  const sorted = [...values].sort((a, b) => a - b);
  const mid = Math.floor(sorted.length / 2);
  return sorted.length % 2 ? sorted[mid] : (sorted[mid - 1] + sorted[mid]) / 2;
}

function timeStartupContext(binary: string, directory: string, home: string): number {
  const start = performance.now();
  const result = spawnSync([binary, "startup-context", "--directory", directory, "--json", "--format", "2"], {
    env: { ...process.env, FORGE614_HOME: home },
  });
  const elapsed = performance.now() - start;
  if (result.exitCode !== 0) throw new Error(`startup-context failed: ${result.stderr?.toString()}`);
  return elapsed;
}

async function timeMemoryContext(binary: string, directory: string, home: string): Promise<number> {
  // Arranca el servidor MCP, hace el saludo del protocolo (initialize + initialized),
  // pide memory_context y mide hasta su respuesta (id 2).
  const start = performance.now();
  const proc = Bun.spawn([binary, "mcp"], {
    env: { ...process.env, FORGE614_HOME: home },
    stdin: "pipe",
    stdout: "pipe",
  });
  const send = (message: object) => proc.stdin.write(JSON.stringify(message) + "\n");
  send({ jsonrpc: "2.0", id: 1, method: "initialize", params: { protocolVersion: "2025-06-18", capabilities: {}, clientInfo: { name: "medicion", version: "1" } } });
  send({ jsonrpc: "2.0", method: "notifications/initialized" });
  send({ jsonrpc: "2.0", id: 2, method: "tools/call", params: { name: "memory_context", arguments: { directory } } });
  proc.stdin.flush();
  const decoder = new TextDecoder();
  let buffer = "";
  let answer: string | null = null;
  outer: for await (const chunk of proc.stdout) {
    buffer += decoder.decode(chunk);
    for (const line of buffer.split("\n")) if (line.includes('"id":2')) { answer = line; break outer; }
  }
  const elapsed = performance.now() - start;
  proc.kill();
  // Sin respuesta a id 2, o con error, la medición no vale (hallazgo 4113885717 de CodeRabbit, PR #18).
  if (answer === null) throw new Error("memory_context: el servidor cerró sin responder");
  // La respuesta de MCP trae el resultado como texto JSON dentro de content[0].text: el error viene escapado
  // (\"error\"), así que se busca con y sin escape (L1-r2 cronometró PROJECT_NOT_BOUND sin notarlo).
  if (answer.includes('"error"') || answer.includes('\\"error\\"') || answer.includes('isError":true')) throw new Error(`memory_context falló: ${answer.slice(0, 300)}`);
  return elapsed;
}

async function main() {
  const binary = process.argv[2] ?? "forge614-engram";
  const directory = process.argv[3] ?? process.cwd();
  const home = process.argv[4] ?? process.env.FORGE614_HOME ?? `${process.env.HOME}/.forge614`;
  const n = Number(process.argv[5] ?? 10);

  const startupTimes: number[] = [];
  for (let i = 0; i < n; i++) startupTimes.push(timeStartupContext(binary, directory, home));

  const contextTimes: number[] = [];
  for (let i = 0; i < n; i++) contextTimes.push(await timeMemoryContext(binary, directory, home));

  console.log(JSON.stringify({
    startupContextMedianMs: median(startupTimes),
    startupContextRuns: startupTimes,
    memoryContextMedianMs: median(contextTimes),
    memoryContextRuns: contextTimes,
  }, null, 2));
}

await main();
```
