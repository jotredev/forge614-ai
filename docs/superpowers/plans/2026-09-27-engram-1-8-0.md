# Engram 1.8.0 — la misma memoria en otra Mac (plan)

> **For agentic workers:** este plan se ejecuta con `superpowers:subagent-driven-development` (una tarea = un subagente con contexto limpio) o `superpowers:executing-plans` (ejecución en línea) según decida quien lo abra; ninguna tarea se empieza sin leer primero su sección completa (Files, Interfaces, Pruebas, Criterio de «hecho»).

**Goal:** publicar `forge614-engram` 1.8.0: la memoria del propietario (proyecto, libreta personal y tablero del ecosistema) queda en Neon (nube) y es la misma en cualquiera de sus dos Mac, sin escritura simultánea, sin que el arranque se sienta más lento, y sin perder nada sin internet. Instalar 1.8.0 y activar la nube en las dos Mac.

**Architecture:** esquema SQLite local nuevo, nivel 12 (enrollment explícito con `cloud on`, igual que el nivel 11 de memoria inteligente); una cola de pendientes (outbox) alimentada por disparadores SQL sobre cada tabla que viaja; una tarea en segundo plano dentro del servidor MCP que sube la cola y baja lo nuevo de una tabla de cambios numerada en Neon (`forge614_sync.changes`); aplicación de cambios bajados con reglas de conflicto por tabla y filtro de secretos; identidad de proyecto por remoto de Git cuando falta `.forge614/project.json`.

**Tech Stack:** Bun + `bun:sqlite` (SQLite local), `Bun.SQL` contra PostgreSQL/Neon (ya en uso, `src/infrastructure/postgres/replica.ts`), TypeScript, `bun test`.

**Spec:** `docs/superpowers/specs/2026-09-27-engram-1-8-0-otra-mac-design.md` (aprobado por el propietario el 2026-09-27), secciones 3–17, decisiones M1–M13.

**Origen:** diseño aprobado el 2026-09-27, reemplaza el esbozo `forge614-engram/.agents/plans/2026-09-23--1.7.0-ecosystem-replication.md` (acta 0024, evolución aditiva).

## Global Constraints

- Todo comando con `rtk` delante; `rtk proxy` para salida sin filtrar.
- Nivel de esquema 12 solo se activa con `cloud on` (D1); sin nube, la base y el arranque no cambian (M5).
- 1.7.2 no abre una base de nivel 12: responde `DATABASE_VERSION`. `cloud on` se corre después de instalar 1.8.0 y de cerrar **todas** las sesiones que usan la base, con el control previo de procesos (guía §4, lección Engram T10/T10b: verificar hora de inicio y programa padre; detenerse si queda alguno anterior).
- `POSTGRES_URL` en `~/.forge614/engram/.env` sigue siendo la única variable de conexión (diseño §10) y apunta a Neon; no hay dos nubes a la vez. El `.env` suma `FORGE614_ENGRAM_INSTALLATION_ID` (D9).
- La dirección de Neon nunca pasa por una sesión de IA: en el uso real, `cloud on` la pide en la terminal del propietario (entrada oculta); en el laboratorio se carga de un archivo sin imprimirla (D13).
- TLS verificado obligatorio fuera de loopback, mismo criterio de `postgresOptions` (`src/infrastructure/postgres/replica.ts:5-23`).
- Espera al arrancar con nube prendida: máximo 1000 ms (`AbortSignal.timeout(1000)` o equivalente), nunca más (M13, D8).
- Ciclo de la tarea en segundo plano: 30 s de intervalo mientras el servidor MCP vive, más un ciclo extra al guardar con retraso corto para agrupar (D7).
- Aviso de cola vieja: pendiente más viejo con más de 24 h → dato en `memory_session_start` (D11, M11).
- Sin nombres de productos externos (acta 0012): revisar `standard/forbidden-mentions.json` antes de escribir cualquier documento de `forge614-ai`.
- Commits convencionales en inglés, sin líneas de atribución ni menciones a ninguna IA.
- Suite como en CI: `FORGE614_TEST_POSTGRES_BIN=$(pg_config --bindir) bun test`; toda prueba omitida se justifica.
- Código literal fuera del plan: cada tarea trae un parche `2026-09-27-engram-1-8-0-t<n>.patch`, probado en laboratorio (copia limpia con `git archive`) antes de entregarse (D12, guía §1).

## Review Focus

Las cinco fallas más probables que ninguna prueba «feliz» cubre, con la prueba que se agrega a la tarea dueña:

1. **La guardia de aplicación no se libera si el aplicador lanza una excepción a mitad de la transacción**, dejando los disparadores apagados para siempre y la cola dejando de crecer con cambios locales reales. → T3: prueba que fuerza un error al aplicar una fila y verifica que, tras el rollback, un guardado local nuevo sí encola.
2. **Reintento infinito y silencioso de un cambio corrupto** (payload que no valida) bloquea el resto de la cola en orden estricto. → T3: prueba de un payload inválido en medio de una tanda; se salta con aviso y sigue con el resto.
3. **La espera de 1000 ms al arrancar no se cancela** si Neon responde justo después del corte, dejando una promesa huérfana que compite por el mismo `sqlite`/conexión con la tarea en segundo plano. → T4: prueba con `AbortSignal` y un mock que resuelve 50 ms después del corte; se verifica que no hay doble aplicación ni excepción no capturada.
4. **`cloud off` no vacía ni marca la cola pendiente**, y una `cloud on` posterior con otra URL de Neon sube filas viejas al proyecto equivocado. → T5: prueba `cloud off` con pendientes en la cola → `cloud status` los sigue mostrando → `cloud on` con otra base → como es otra nube (D14), vuelve a encolar toda la memoria local y baja desde 0; con la misma base, la cola y `last_applied_id` se conservan.
5. **Identidad por remoto de Git compara mal direcciones equivalentes** (con y sin `.git`, `git@`/`ssh://` vs `https://`, mayúsculas de host) y crea proyectos duplicados. → T3: banco de pares equivalentes/no equivalentes (incluye con y sin credenciales embebidas, con y sin puerto) como prueba fija.

## Decisiones

- **D1.** Nivel de esquema 12 en la misma base SQLite, activado SOLO por `cloud on` (enrollment explícito, igual que el 11). Sin nube, la base no cambia y el arranque es el de hoy. Contiene: cola de pendientes (tabla outbox), el número del último cambio aplicado desde Neon, el origen de cada cambio y los avisos pendientes (conflicto, cola vieja). Motivo: la cola se escribe en la MISMA transacción que el guardado, así no se pierde nada si se cierra la laptop. Consecuencia: 1.7.2 no abre una base de nivel 12 (responde `DATABASE_VERSION`); por eso `cloud on` se corre después de instalar 1.8.0 y cerrar todas las sesiones que usan la base (lección de la guía §4, Engram T10/T10b). *(Decisión técnica del orquestador, a confirmar por el propietario; alternativa descartada: base aparte `sync.db` — no toca el esquema, pero el guardado y la cola no quedan en una misma transacción.)*
- **D2.** La cola se alimenta con disparadores SQL (triggers) de nivel 12 sobre cada tabla que viaja (sección 5 del diseño); al aplicar cambios bajados de Neon, los disparadores no vuelven a encolar (guardia de una fila que el aplicador prende y apaga dentro de su transacción). Cada fila de la cola lleva la imagen completa de la fila cambiada (JSON), el tipo (tabla) y la operación.
- **D3.** En Neon: `forge614_sync.changes(id bigserial primary key, installation_id uuid not null, kind text not null, payload jsonb not null, created_at timestamptz not null default now())`, creada si falta; las tablas `revisions`/`state` de hoy no se tocan. Misma variable `POSTGRES_URL` y misma verificación de TLS fuera de loopback (`replica.ts:5-23`).
- **D4.** Conflicto de recuerdos: si llega una versión de un recuerdo que localmente ya cambió desde la base común, se guardan las dos como versiones; queda activa la de fecha más reciente; la otra queda en el historial; se registra un aviso que se muestra una vez en el siguiente `memory_session_start` (junto a `sessionNotice`, como dato). Nunca se detiene la sincronización. Las demás tablas: la fila más reciente gana, sin aviso (sesiones, resúmenes, grupos, pertenencias, fuentes).
- **D5.** El filtro de secretos se aplica a lo que llega de Neon antes de escribir (un cambio rechazado se salta y queda un aviso; no detiene la sincronización). Campos de texto que viajan y necesitan prueba propia (D5): `memories.title`, `memories.content`, `sessions.kind`, `sessionSummaries` (contenido del resumen si lo lleva), `ecosystem_groups` (nombre/descripción), `ecosystem_sources` (lo que identifique la fuente), `confirmations`/`confirmationRequests` (si llevan texto libre) — **ver «Dudas para el orquestador»**: T1/T3 deben confirmar contra el código real qué columnas de estas tablas son texto libre versus enumeraciones/ids, y agregar la prueba exacta por cada una.
- **D6.** Identidad por remoto de Git: solo al aplicar un cambio de un proyecto que no existe localmente; se compara la dirección normalizada de `origin` (sin credenciales, sin `.git` final, https y ssh equivalentes) con la de las carpetas de proyectos locales conocidas; si no hay coincidencia, se crea como proyecto nuevo sin carpeta; nunca se adivina.
- **D7.** Tarea en segundo plano dentro del servidor MCP (`server.ts`): arranca solo si hay nube configurada y el nivel es 12; ciclo: subir cola en orden, bajar lo posterior al último número, aplicar; intervalo de 30 s mientras el servidor vive y un ciclo al guardar (con retraso corto para agrupar). Errores de red: se reintenta en el siguiente ciclo, sin ruido.
- **D8.** Espera al arrancar (M13): `startup-context` y `memory_context`, con nube prendida, hacen un ciclo de bajada con tope de 1000 ms (`AbortSignal`/timeout); si no termina, siguen con lo local.
- **D9.** Id de instalación: UUID en `~/.forge614/engram/.env` como `FORGE614_ENGRAM_INSTALLATION_ID`, generado por `cloud on`. `cloud on --postgres-url <url>` prueba la conexión (`validatePostgres`) antes de escribir; `cloud off` quita `POSTGRES_URL` (conserva el id y la base de nivel 12, que sigue funcionando sin nube); `cloud status` (con `--json`): prendida/apagada, id de instalación, último cambio aplicado, pendientes en la cola, hora del pendiente más viejo.
- **D10.** `sync` = un ciclo ahora (subir+bajar) con el mecanismo nuevo; `sync-watch` = el mismo ciclo por intervalo, marcado obsoleto con sunset 2027-03-31 (aviso en stderr y en `help`); `sync --upgrade-format` y los formatos 1–3 quedan obsoletos, sin borrar código (acta 0024).
- **D11.** Aviso de cola vieja (M11): si el pendiente más viejo tiene más de 24 h, `memory_session_start` lo dice como dato.
- **D13.** `cloud on` sin argumentos pide la dirección en la terminal con entrada oculta y la prueba antes de guardarla; `--postgres-url <url>` queda para pruebas y laboratorio. En T9 y T10 el propietario corre `cloud on` en su propia terminal (fuera de toda sesión de IA), así la dirección no entra a ningún registro. *(Decisión técnica del orquestador, a revisar.)*
- **D14.** Primera sincronización (M4): `enableCloud` encola **toda** la memoria local que viaja, en la misma transacción y en orden de dependencias (proyectos, grupos, pertenencias, fuentes, recuerdos, versiones, datos de memoria inteligente, sesiones, entradas, resúmenes, confirmaciones). `cloud_state` guarda una huella de la base remota (servidor y nombre de base, sin usuario ni contraseña); si `cloud on` apunta a otra base, se trata como primera vez: se vuelve a encolar todo y se baja desde 0. *(Decisión técnica del orquestador, a revisar.)*
- **D12.** Forma del plan: el plan fija por tarea archivos y líneas reales, interfaces exactas (nombres y tipos), SQL de las tablas nuevas, y la lista de pruebas con lo que cada una afirma. El código literal NO va en el plan: sale de un laboratorio del orquestador por tarea (parche probado en copia limpia) y se agrega al plan como `2026-09-27-engram-1-8-0-t<n>.patch` antes de entregar la tarea, igual que en 1.7.2. Cada tarea trae «**Parche:** se agrega tras el laboratorio.» y «**Cierre de T<n>:**» vacío.

- Nuevas tablas SQLite (nivel 12), DDL exacto:
  ```sql
  CREATE TABLE cloud_outbox (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    kind TEXT NOT NULL,
    op TEXT NOT NULL CHECK (op IN ('insert','update','delete')),
    payload TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
  );
  CREATE TABLE cloud_state (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    last_applied_id INTEGER NOT NULL DEFAULT 0,
    apply_guard INTEGER NOT NULL DEFAULT 0
  );
  CREATE TABLE cloud_notices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL,
    payload TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
    shown INTEGER NOT NULL DEFAULT 0
  );
  ```
  `cloud_state` lleva además `remote_fingerprint TEXT` (D14). `cloud_state` tiene una sola fila (`id=1`), insertada por `enableCloud` al activarse; `apply_guard` es la guardia de D2 (0 = disparadores activos, 1 = el aplicador está escribiendo y los disparadores no vuelven a encolar).

## Medición del arranque

Mediana de 10 corridas en tiempo de `forge614-engram startup-context --directory <ruta-absoluta> --json --format 2` (los argumentos que usa el gancho de Engines 1.13.0, `forge614-engines/src/infrastructure/engram/startup-context-client.ts:216-217`; el gancho no pone tope de tiempo) y de `memory_context` por MCP. Criterios: sin nube igual que 1.7.2 ±2 ms (misma máquina, misma base copiada); con nube ≤ 1 s más en el peor caso, anotando despierta y dormida (Neon suspendida). En tokens: presupuesto de acta 0027 §8 (≤3000 caracteres de bloque + manual).

Script del orquestador (`medir-arranque.ts` en su scratchpad; no entra al repositorio de Engram). Antes de usarlo en L1 se prueba contra 1.7.2 y una base copiada: si el saludo MCP o los argumentos no cuadran, se corrige aquí.

```typescript
#!/usr/bin/env bun
// medir-arranque.ts — mediana de N corridas de startup-context y memory_context
import { spawnSync } from "bun";

function median(values: number[]): number {
  const sorted = [...values].sort((a, b) => a - b);
  const mid = Math.floor(sorted.length / 2);
  return sorted.length % 2 ? sorted[mid] : (sorted[mid - 1] + sorted[mid]) / 2;
}

function timeStartupContext(binary: string, directory: string, home: string): number {
  const start = performance.now();
  const result = spawnSync([binary, "startup-context", "--directory", directory, "--json", "--format", "2"], {
    env: { ...process.env, FORGE614_HOME: home },
  });
  const elapsed = performance.now() - start;
  if (result.exitCode !== 0) throw new Error(`startup-context failed: ${result.stderr?.toString()}`);
  return elapsed;
}

async function timeMemoryContext(binary: string, directory: string, home: string): Promise<number> {
  // Arranca el servidor MCP, hace el saludo del protocolo (initialize + initialized),
  // pide memory_context y mide hasta su respuesta (id 2).
  const start = performance.now();
  const proc = Bun.spawn([binary, "mcp"], {
    env: { ...process.env, FORGE614_HOME: home },
    stdin: "pipe",
    stdout: "pipe",
  });
  const send = (message: object) => proc.stdin.write(JSON.stringify(message) + "\n");
  send({ jsonrpc: "2.0", id: 1, method: "initialize", params: { protocolVersion: "2025-06-18", capabilities: {}, clientInfo: { name: "medicion", version: "1" } } });
  send({ jsonrpc: "2.0", method: "notifications/initialized" });
  send({ jsonrpc: "2.0", id: 2, method: "tools/call", params: { name: "memory_context", arguments: { directory } } });
  proc.stdin.flush();
  const decoder = new TextDecoder();
  let buffer = "";
  outer: for await (const chunk of proc.stdout) {
    buffer += decoder.decode(chunk);
    for (const line of buffer.split("\n")) if (line.includes('"id":2')) break outer;
  }
  const elapsed = performance.now() - start;
  proc.kill();
  return elapsed;
}

async function main() {
  const binary = process.argv[2] ?? "forge614-engram";
  const directory = process.argv[3] ?? process.cwd();
  const home = process.argv[4] ?? process.env.FORGE614_HOME ?? `${process.env.HOME}/.forge614`;
  const n = Number(process.argv[5] ?? 10);

  const startupTimes: number[] = [];
  for (let i = 0; i < n; i++) startupTimes.push(timeStartupContext(binary, directory, home));

  const contextTimes: number[] = [];
  for (let i = 0; i < n; i++) contextTimes.push(await timeMemoryContext(binary, directory, home));

  console.log(JSON.stringify({
    startupContextMedianMs: median(startupTimes),
    startupContextRuns: startupTimes,
    memoryContextMedianMs: median(contextTimes),
    memoryContextRuns: contextTimes,
  }, null, 2));
}

await main();
```

Uso: `rtk bun run medir-arranque.ts <binario> <directorio> <home> <n>`, con una copia de la base en `<home>` (nunca la real); correr una vez sin nube (`cloud off` en el `home` de prueba) y dos veces con nube (Neon despierta y recién suspendida, forzando la suspensión con el tiempo de inactividad del plan gratuito de Neon o esperando el intervalo real).
